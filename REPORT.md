# CI failure analysis

Analysis date: 2026-08-08

Repository: [AmigaPorts/m68k-amigaos-gcc](https://github.com/AmigaPorts/m68k-amigaos-gcc)

## Executive summary

There are two separate problems, and GitHub's UI makes them look like one:

1. The repository does not currently use GitHub Actions. The visible red commit statuses are published by Jenkins.
2. The current August 8 build has a high-confidence source-level failure: the two newly added CD32/CDTV SDK downloads use an HTTPS server whose certificate chain is rejected by both `curl` and `wget`.

Several older red results are not compiler-image failures. The compiler image was built and published successfully, but the parent Jenkins job was marked failed when a synchronously triggered downstream `docker-amiga-gcc` job failed or was aborted.

## 1. No GitHub Actions are configured

The repository contains no `.github/workflows` directory. GitHub's public API also reports zero workflows and zero workflow runs:

- [GitHub Actions page](https://github.com/AmigaPorts/m68k-amigaos-gcc/actions)
- [Workflow inventory](https://api.github.com/repos/AmigaPorts/m68k-amigaos-gcc/actions/workflows?per_page=100)

The status context attached to commits is `continuous-integration/jenkins/branch`. Therefore, the red status shown by GitHub is generated by Jenkins rather than GitHub Actions.

The repository still contains a legacy `.travis.yml`, but it is not responsible for the current status reports.

## 2. Current August 8 failure

The current failure is Jenkins build 158 on commit `d8a3a8757af2`, `sdk: add CD32 and CDTV development headers`:

- [Current commit status history](https://api.github.com/repos/AmigaPorts/m68k-amigaos-gcc/statuses/d8a3a8757af2fadcb7eed2e02f711d72f0a08aff?per_page=100)
- Started: 2026-08-08 19:32:12 UTC
- Failed: 2026-08-08 19:58:01 UTC

### High-confidence root cause

The new SDK descriptors use these URLs:

- [`sdk/cd32.sdk`](sdk/cd32.sdk#L3): `https://www.cd32-allianz.de/downloads/software/CD32_DeveloperKit.lha`
- [`sdk/cdtv.sdk`](sdk/cdtv.sdk#L3): `https://www.cd32-allianz.de/downloads/software/CDTV_DeveloperKit.lha`

Both URLs currently fail certificate verification:

```text
curl: (60) SSL certificate OpenSSL verify result:
unable to get local issuer certificate (20)
```

`wget` rejects the same certificate chain. The corresponding HTTP URLs return `200 OK`, but switching to unverified HTTP without integrity checking would introduce a supply-chain risk.

The failure reaches the Docker build through the following path:

1. [`Makefile`](Makefile#L1028) discovers every `sdk/*.sdk` descriptor and adds it to `all-sdk`.
2. [`Dockerfile`](Dockerfile#L27) executes `make ... all-sdk`.
3. [`.dockerignore`](.dockerignore#L2) excludes the download cache, so a clean Docker build must download both archives.
4. [`sdk/install`](sdk/install#L33) selects `curl` whenever it is installed.
5. A failed curl request removes the partial file and exits immediately. `wget` is used only when curl is absent; it is not a fallback after a curl failure.

The archives themselves were checked independently:

- Both expected archives extract successfully.
- Every path named by `cd32.sdk` and `cdtv.sdk` exists.
- Both SDK installation routines complete successfully when the archives are already available.
- The resulting headers and FD files are installed in the intended prefix paths.

Known archive hashes from the verified local copies are:

```text
05c53b907ab3ea5874cec9b79b45eb8d760d51b569421d9f556ac2b41124d318  CD32_DeveloperKit.lha
5497a8fefca8ade4a509f655eb4a4b3737b9652c16d8cdf934c76fe2dfbe0674  CDTV_DeveloperKit.lha
```

The private Jenkins console returns HTTP 403 to anonymous users, so the exact failing log line from build 158 could not be quoted. Nevertheless, the TLS error is directly reproducible, occurs in the only functional change introduced by the commit, and is on a mandatory clean-build path.

### Remediation implemented on August 9

The working tree now implements the upstream fix in the shared SDK installer rather than adding a Docker-only workaround:

- `cd32.sdk` and `cdtv.sdk` declare explicit HTTP fallback URLs and pinned SHA-256 hashes.
- Downloads go to temporary files and become cache entries only after successful verification.
- HTTPS remains the primary source; HTTP is attempted only after the primary source fails.
- An SDK descriptor cannot declare `FallbackUrl` without also declaring `Sha256`.
- Existing cached archives with checksums are verified before use. A bad cache entry and its corresponding extraction directory are discarded before retrying.
- Linux `sha256sum` and the macOS-provided `shasum -a 256` are both supported.
- SDK descriptors without the new metadata retain their previous behavior.

Isolated tests covered fresh curl and wget downloads, the live TLS failure and HTTP fallback, both SDK installations, portable `shasum` verification, corrupted-cache recovery, rejection of fallback metadata without a checksum, and compatibility with a legacy descriptor.

## 3. Historical red statuses include downstream false failures

The Jenkins pipeline builds and publishes `amigadev/m68k-amigaos`, then synchronously triggers `docker-amiga-gcc`:

```groovy
build(job: "${v}/${env.BRANCH_NAME}", wait: true, ...)
```

See [`Jenkinsfile`](Jenkinsfile#L112).

Because the downstream call propagates its result, a downstream packaging failure marks the parent compiler-image job red even if the compiler image was built and published successfully.

### Conclusive June 29 example

For parent Jenkins build 157:

| Time (UTC) | Event |
|---|---|
| 22:46-22:47 | Both `m68k-amigaos` architecture images and the `latest` manifest were pushed |
| 22:48:16 | Downstream `docker-amiga-gcc` build 234 started |
| 22:50:28 | Downstream build 234 failed |
| 22:50:30 | Parent build 157 was marked failed |
| 22:50:29-22:52:26 | Downstream retry 235 ran and succeeded |

Evidence:

- [`amigadev/m68k-amigaos:latest` metadata](https://hub.docker.com/v2/repositories/amigadev/m68k-amigaos/tags/latest)
- [`docker-amiga-gcc` status history](https://api.github.com/repos/AmigaPorts/docker-amiga-gcc/statuses/ba2e2d5b91d6b4393a00c84575371e53d99f5322?per_page=100)
- [Parent commit status history](https://api.github.com/repos/AmigaPorts/m68k-amigaos-gcc/statuses/7d3e35f58e61bdf325d84b912b139f973d9b7452?per_page=100)

The same timing relationship appears elsewhere:

- February 11: downstream build 230 failed at 10:37:35 UTC; parent build 154 failed two seconds later.
- April 18: downstream build 231 was aborted at 21:05:34 UTC; parent build 155 failed three seconds later.

These results describe failure of the chained pipeline as a whole, not necessarily failure of the `m68k-amigaos` compiler image.

## 4. The history was not continuously broken

GitHub displays the latest status for a commit and context. A later failed rerun can therefore replace a previously green visible status without changing the source commit.

Examples:

| Commit | Successful run | Later result |
|---|---:|---|
| `184f8e0` | 143 | Run 144 was aborted by a newer build |
| `9878776` | 145 | Run 152 later failed |
| `8bce7e6` | 153 | Run 154 later failed because the downstream job failed |

See the [status history for `8bce7e6`](https://api.github.com/repos/AmigaPorts/m68k-amigaos-gcc/statuses/8bce7e62b001558ac5d3a854e6e3b5a163363d77?per_page=100).

This explains why the repository appears to have been broken continuously even though successful builds occurred between the red results.

## 5. PR builds are structurally unsupported

The build and manifest functions accept only `master` and `dev`. Any other `BRANCH_NAME` throws `Invalid branch, stopping build!`:

- [`Jenkinsfile`](Jenkinsfile#L48)
- [`Jenkinsfile`](Jenkinsfile#L84)

Jenkins multibranch pull-request jobs normally use names such as `PR-23`, so a PR build that reaches this code will fail by design. This should be corrected independently of the SDK download failure.

## 6. Reproducibility and maintenance risks

The build has several moving inputs that allow the same commit to produce different results over time:

- [`Dockerfile`](Dockerfile#L1) uses `amigadev/docker-base:latest`.
- The base image itself is built from `debian:unstable-slim`.
- The build clones live dependency branches listed in [`default-repos`](default-repos).
- SDKs are downloaded from external hosts without pinned checksums.
- Additional files are fetched from live `master` branches in the Dockerfile.
- Jenkins uses the controller label `master` and directly accesses `Jenkins.instance`, both of which are fragile across Jenkins upgrades and security-policy changes.
- Jenkins logs are not readable anonymously, making public failure diagnosis difficult.

These moving inputs explain how rerunning an unchanged source commit can change from green to red.

## Recommended fix order

### Priority 0: restore the current build

1. The working tree now provides checksum-protected fallback and cache verification.
2. As a longer-term improvement, repair the certificate chain on `www.cd32-allianz.de`, or use a stable HTTPS mirror if redistribution is permitted.
3. Do not use `curl -k` or otherwise disable TLS verification.

### Priority 1: make CI status accurate

1. Stop propagating the downstream `docker-amiga-gcc` result as the compiler-image result.
2. Trigger the downstream build asynchronously, use `propagate: false` and inspect its result, or publish separate status contexts for compiler-image and downstream packaging jobs.
3. Mark the parent compiler-image build successful once its architecture images and manifest have been published successfully.

### Priority 2: restore PR validation

1. Accept Jenkins PR branch names such as `PR-*`.
2. Separate branch-dependent publication policy from compilation and validation. PRs can build/test without publishing production tags.

### Priority 3: add visible, reproducible validation

1. Add a lightweight GitHub Actions workflow for shell syntax, SDK descriptor validation, archive checksum verification, and isolated SDK installation tests.
2. Keep the credentialed multi-architecture publish pipeline in Jenkins if necessary, but expose its logs or publish actionable failure summaries.
3. Pin the Docker base image by digest and pin dependency repositories to known revisions or release tags.

## Conclusion

The current August failure is a real build regression caused by certificate verification on the newly added SDK downloads. The longer historical pattern is largely a CI-reporting problem: successful compiler-image builds are marked red when a chained downstream packaging job fails, and later reruns overwrite earlier green statuses.

The archive transport and integrity fix is now implemented and passes isolated live-download tests. Separating parent and downstream statuses remains necessary to make future failures accurately represent which artifact actually failed.
